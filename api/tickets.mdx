EarthCoop has a real support-ticket domain and current API routes used by the application. The API surface is nevertheless **evolving / In development** and is **not a stable public external contract**. This page records verified implementation boundaries rather than promising that every current route, field, workflow detail, or response shape will remain unchanged for third-party clients.

## Current implementation

The current support subsystem includes ticket creation and lifecycle capabilities, member-visible ticket surfaces, comments/attachments in the support domain, and application routes/controllers for working with tickets.

The precise route methods and payload structures are implementation details until a versioned client contract is explicitly published.

## Ticket identity and ownership

A ticket belongs to a support context and may be associated with an authenticated member and related identifying information. Any API operation must still enforce the applicable ownership/access policy; knowing a numeric ticket ID or tracking code must not grant access to another member's support case.

## Creation

Where the current API permits ticket creation, the request is validated and the support domain creates the ticket under its own rules. This guide does not promise a guaranteed priority decision, confirmation email, fixed SLA calculation, or one immutable tracking-code format unless the specific current service and contract explicitly establish those behaviors.

<Warning>
  A request reaching a ticket route does not bypass validation, authentication, authorization, attachment policy, or support-domain workflow rules.
</Warning>

## Listing and reading tickets

Current routes can expose a member's own tickets and ticket details. Filtering, pagination, included relationships, and JSON field names may evolve. External clients should therefore not hard-code today's internal response shape as a long-term public contract.

## Updating and closing

Ticket state changes are domain actions. Whether a member can update priority/category, close a ticket, reopen it, or add a comment depends on the current support service and authorization rules.

A comment, close operation, or status change should leave the appropriate support-domain history rather than silently rewriting earlier facts.

## Attachments and comments

The support domain can include comments and attachments. Allowed file types, limits, storage behavior, and download authorization are operational/security controls and may change. Do not rely on an old guide's fixed file-extension list as a permanent external API guarantee.

## NajmHoda escalation

NajmHoda can interact with the support-ticket subsystem through conditional escalation logic. That integration does not mean any chat message automatically becomes a ticket. The current orchestration/policy decides whether escalation criteria are met and the support service remains responsible for creating the formal support record.

## Authentication

Some current ticket routes are protected by the application's authentication stack. The existence of those routes does not establish a documented general-purpose public token-issuance flow for external clients.

## Stability guidance

For first-party maintenance, inspect the current route, controller/service, policies, models, and tests. For native or third-party clients, use only the future explicitly versioned support API contract once it is published.

```text
current ticket route ≠ stable public API
chat escalation ≠ automatic ticket creation
support record + authorization + domain history = authoritative workflow
```
