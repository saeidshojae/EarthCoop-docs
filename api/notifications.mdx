EarthCoop has current notification capabilities and API routes used by the application, but this surface is **evolving / In development** and is **not a stable public external contract**. Notification classes and routes prove current domain behavior; they do not guarantee that every payload field, route method, or client-facing representation is frozen for external consumers.

## Current product behavior

The current application can generate notifications for domain events such as project review decisions and other product workflows. Authenticated notification routes also exist for viewing and managing a member's notifications.

The exact set of notification types can change as EarthCoop domains evolve. This guide therefore does not define a permanent closed list of event types.

## Payload boundary

A notification payload is a presentation/integration record about another domain event. It is not itself the authoritative record of that event.

For example:

- a project approval notification is not the project review history itself;
- an investment-related notification is not proof that a NajmBahar Transfer occurred;
- an amount shown in a notification does not override the monetary ledger;
- a governance notification does not create a vote, appointment, or legal decision.

When a notification refers to money, the EarthCoop monetary unit is **Bahar**; **Gol is the subunit of Bahar**. Internal storage or payload precision in Gol must not be described as a separate currency.

## Authentication and ownership

Current member notification routes are tied to authenticated application context. A valid request must still be scoped to the authenticated member so one user cannot read or mutate another user's notification merely by supplying an identifier.

The existence of an authenticated route does not prove a general public bearer-token issuance workflow. See the API authentication guide for that boundary.

## Read and delete operations

Current application routes can support operations such as retrieving notifications, marking a notification as read, and deleting a notification where the implementation permits it. The exact HTTP method, JSON response, and identifier representation remain implementation details while the stable external API is **In development**.

## Domain truth vs notification truth

For high-impact actions, always verify the source domain:

```text
notification → points to an event
project/election/support record → domain truth
NajmBahar ledger → monetary truth
```

A client should never infer a payment, refund, project completion, or economic guarantee solely from a notification label.

## Stability guidance

For first-party development, inspect the current notification classes, controllers/routes, and tests. For third-party or native clients, wait for the explicitly versioned notification contract and its documented payload schemas.

Until that contract is published, the current notification payload is **not a stable public payload contract**.
