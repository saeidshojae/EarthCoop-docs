EarthCoop has real HTTP routes under `/api`, but the current route file contains a mixture of application endpoints, legacy compatibility paths, closure-based geographic helpers, and newer controller-backed services. This surface is **evolving / In development** and is **not a stable public API contract** for third-party or native clients yet.

## Current status

The current repository proves that API routes exist for several domains, including NajmHoda, support-related capabilities, notifications, account/user access, and geographic/location data. Route existence is implementation evidence; it does not by itself establish a versioned external contract, compatibility guarantee, or supported SDK surface.

<Warning>
  Do not build a long-lived external integration by assuming every current `/api` route, payload, authentication mechanism, or response field is frozen. Stable client/mobile API work remains a separate product-readiness task.
</Warning>

## Base path

Current application routes are mounted under:

```text
/api
```

There is no general version prefix that turns the whole current file into a stable `/v1` public contract. A future stable client API may therefore differ from legacy/current internal paths.

## Authentication

Some current routes use Laravel Sanctum authentication, including routes protected by `auth:sanctum`. This establishes an authentication mechanism for those implementation paths; it does not prove that EarthCoop currently publishes a general-purpose external token-issuance workflow.

See [Authentication](/api/authentication) for the verified boundary.

## Response contracts

Different current controllers and legacy closure routes can return different JSON shapes. Do not assume one universal envelope such as `{ success, data, meta }` unless the specific controller or future stable API specification defines it.

For implementation work, verify the exact current route and controller. For a public/mobile client, wait for or use the explicitly versioned contract designated for that client rather than inferring stability from present Laravel routes.

## Authorization and domain rules

Authentication answers only who the requester is. Each protected operation can also require domain authorization, ownership, role, policy, governance topology, monetary state, or other business rules.

For action-capable NajmHoda paths in particular, client/browser context cannot grant authority. Trusted server-side policy and domain services decide whether a mutation is permitted.

## Legacy and canonical location routes

The current API file still contains older geography/location helpers alongside the newer canonical location/governance architecture. Their presence is one reason the entire `/api` file must not be described as the final external geographic contract.

## Integration guidance

For internal development, treat the checked-in route/controller code and tests as the implementation source of truth. For third-party or native-client integrations, treat the stable versioned API specification—once explicitly published—as the contract. Until then, the current `/api` surface remains **In development** from the perspective of a durable public API.
