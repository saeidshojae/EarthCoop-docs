Some current EarthCoop API routes are protected by Laravel Sanctum, including routes using the `auth:sanctum` middleware. This proves that authenticated requests are part of the current application architecture. It does **not** prove that ordinary web login automatically issues a reusable personal access token for external integrations.

## Verified current boundary

The repository currently shows Sanctum-protected routes and authenticated controllers. A request reaching such a route must satisfy the authentication mechanism configured by the running EarthCoop application and then pass any additional domain authorization checks.

Authentication and authorization are different:

- **authentication** establishes the requesting identity/session/credential;
- **authorization** determines whether that identity may perform the requested operation;
- domain services can impose further ownership, role, policy, governance, or monetary constraints.

## Public token issuance

There is **no verified public token issuance flow documented** in the current repository evidence used for this guide. In particular, this documentation does not claim that:

- ordinary `/login` returns a personal access token;
- every member has a token-management screen;
- a public password-to-token endpoint is a supported integration contract;
- external tokens have a particular lifetime, renewal rule, or revocation UI.

Those behaviors must be documented only when a specific current route/controller and supported product contract prove them.

<Warning>
  Do not send member credentials to a guessed API endpoint in order to obtain a token. A route being protected by `auth:sanctum` does not create a public credential-issuance API.
</Warning>

## Bearer credentials where explicitly provisioned

If a trusted EarthCoop deployment or future stable API explicitly provisions a Sanctum-compatible bearer credential through an authorized channel, the client can send it using the normal HTTP authorization header:

```http
Authorization: Bearer YOUR_AUTHORIZED_TOKEN
Accept: application/json
```

That example describes how a bearer credential is presented. It is not a claim about how a credential is currently issued to general users.

## Session-authenticated application requests

EarthCoop's own web application can use the authentication mechanisms configured for its first-party flows. First-party browser behavior should not be conflated with a supported external-token contract. A future native/mobile authentication design may introduce a versioned client contract with its own issuance, refresh, expiry, and revocation rules.

## NajmHoda and action authority

Even after authentication, NajmHoda does not receive arbitrary mutation authority from request context. The server applies entry policy, ownership checks, page/domain resolution, and the applicable service authorization before an action-capable path can proceed.

A valid credential therefore means “the server knows who is making this request,” not “the requester may do anything represented by a route.”

## Error handling

Protected routes can reject an unauthenticated request. The exact response shape is part of the specific current controller/middleware behavior and should not be generalized into one immutable public API format while the external API remains **In development**.

## External client status

EarthCoop's durable, versioned external/mobile authentication contract is still **In development**. Until it is explicitly published, developers should treat the existing Sanctum-protected routes as implementation evidence rather than a promise of a stable public token lifecycle.
