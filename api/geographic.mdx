EarthCoop currently exposes several geographic/location routes under `/api`, but this family is **evolving / In development** and is **not a stable public external contract**. The application still contains **legacy** geography helpers alongside the newer **canonical location/governance** model.

## Why the distinction matters

The current EarthCoop location architecture is topology-aware. It supports governance areas and residence paths that cannot be accurately reduced to one fixed sequence such as “province → city → neighborhood” for every place in the world.

Examples include:

- cities with no regions;
- regions with no neighborhoods;
- villages with no neighborhoods;
- rural branches;
- optional local micro-levels such as Street, Alley, Complex, Block, and Building;
- pending proposed locations that can participate in the registration/governance workflow before final administrative approval under the applicable rules.

A legacy route returning children at one level must therefore not be interpreted as the complete governance model.

## Current route families

The present application contains older helper routes such as province/county/district/city/village lookups and broader geographic child traversal routes. These can still be useful to first-party code or compatibility flows, but their existence does not make them the final client-facing location contract.

<Warning>
  Do not build a durable external location client around the assumption that the current legacy hierarchy, identifier prefixes, or response shapes are permanent. The stable canonical client/mobile contract remains to be versioned and published.
</Warning>

## Canonical location/governance model

The canonical model separates at least these concepts:

- reference geographic entities;
- the member's primary residence;
- governance areas derived from actual topology;
- official system-group membership dimensions;
- optional community/micro-location membership;
- proposed/pending locations and their support/approval lifecycle.

That model is the correct conceptual basis for new development. Current legacy API helpers should be treated as adapters or implementation history where they do not express the full model.

## Authentication and exposure

Some existing geography helpers may currently be reachable without authenticated user context. That implementation fact must not be generalized into a promise that all future canonical location APIs will be public or unauthenticated.

## Response shapes

Legacy helpers can return different shapes and identifiers. A route may return plain objects, arrays, or compatibility identifiers used by older cascading selectors. Those formats are implementation details until the stable canonical API specification is published.

## Guidance for developers

For current first-party maintenance, inspect the exact route, service, and tests in the application repository. For new third-party or native-client work, use the future explicitly versioned canonical location/governance contract rather than treating legacy helpers as the recommended permanent API.

```text
legacy geography route ≠ canonical governance model
current response shape ≠ stable public contract
canonical topology + versioned client API = target contract
```
