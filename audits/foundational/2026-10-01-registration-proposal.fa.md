# پیشنهاد کنترل‌شده ثبت بسته اسناد بنیادین EarthCoop

**تاریخ:** 2026-10-01  
**وضعیت:** پیشنهاد اجرایی برای تصمیم بنیان‌گذار — اعمال‌نشده  
**پیش‌نیاز:** بسته‌شدن Package F با CI سبز و صفر blocker باز

> این سند اجازه ثبت نیست. هیچ مرحله‌ای از این پیشنهاد نباید فقط به دلیل آماده‌بودن فنی اجرا شود. شروع عملیات ثبت نیازمند تصمیم صریح بنیان‌گذار درباره خودِ ثبت و وضعیت نفاذ اسناد است.

---

## ۱. موضوع تصمیم مورد نیاز

بنیان‌گذار باید به‌صورت صریح تعیین کند که آیا بسته زیر به‌عنوان release حقوقی جدید **ثبت** شود یا خیر:

- FC 1.2
- CH 1.1
- CO 1.1
- EX 1.2
- ECON 0.3
- DG 0.3
- JUD 0.3
- LOC 0.3
- ETH 0.3
- STD 0.3
- ECON-REF-01 0.2 به‌عنوان سند مرجع غیرتقنینی

تصمیم درباره **ثبت** از تصمیم درباره **لازم‌الاجرا/نافذ شدن** و نیز از تصمیم درباره **public baseline** جداست. این سه وضعیت نباید به‌صورت ضمنی به یکدیگر گره بخورند.

---

## ۲. ترتیب پیشنهادی عملیات پس از اجازه صریح

۱. از همان commit بازبینی‌شده و سبز، متن‌های کامل consolidated، provenance و Concordance دوباره به‌صورت deterministic تولید شوند.

۲. یک registered release snapshot جدید و immutable ساخته شود که دست‌کم شامل متن کامل هر نسخه، provenance، Concordance، شناسه commit منبع، تاریخ، مرجع تصمیم و وضعیت حقوقی دقیق باشد.

۳. صورت‌ثبت Founder Decision مشخص کند برای هر سند کدام وضعیت اعمال می‌شود: registered-not-effective، effective یا هر وضعیت معتبر دیگری که مدل registry اجازه می‌دهد. هیچ وضعیت از روی نام فایل یا pipeline حدس زده نشود.

۴. registry داخلی release و سپس traceability در `document-registry.json` مطابق `REGISTRY_MODEL.md` به registered release جدید متصل شود. root registry نباید یک draft را به‌عنوان authority معرفی کند.

۵. `docs-manifest.json` فقط برای renditionهایی به‌روزرسانی شود که واقعاً source معتبر و وضعیت ترجمه/بازبینی روشن دارند. Manifest منبع اثر حقوقی نیست و نباید وضعیت registration/effectiveness را خودش اختراع کند.

۶. public baseline در checkpoint جداگانه بررسی شود. ثبت release جدید نباید به‌صورت خودکار baseline عمومی را جابه‌جا کند. اگر baseline باید ارتقا یابد، آن تصمیم و validation مستقل ثبت شود.

۷. پس از هر تغییر authority-state، validation کامل registry، manifest، translation freshness، Docs Center و release traceability اجرا شود و snapshot تاریخی قبلی بدون تغییر باقی بماند.

---

## ۳. قواعد fail-closed ثبت

عملیات باید متوقف شود اگر هر یک از وضعیت‌های زیر رخ دهد:

- commit مورد ثبت با commit بازبینی‌شده متفاوت باشد؛
- متن کامل تولیدشده با provenance/Concordance مورد بازبینی تطبیق نکند؛
- یک شناسه ماده حذف، تکرار، renumber یا reuse شده باشد؛
- فراداده رابطه اسنادی دوباره hierarchy قدیمی را احیا کند؛
- registry و release snapshot درباره نسخه یا وضعیت سند اختلاف داشته باشند؛
- سندی به‌اشتباه effective یا public-current شود؛
- translation/locale غیرواقعی، به‌ویژه محتوای legacy `ar/` به‌عنوان ترجمه عربی، وارد manifest شود؛
- registered release تاریخی برای جا دادن نسخه جدید overwrite شود.

---

## ۴. سیاست نفاذ پیشنهادی

Package F درباره اینکه همه نسخه‌ها باید همان لحظه لازم‌الاجرا شوند تصمیم نگرفته است. بنابراین امن‌ترین مدل ثبتی این است که **ثبت و نفاذ دو action مستقل** باقی بمانند.

اگر تصمیم بنیان‌گذار صرفاً «ثبت بسته بازنگری‌شده» باشد، pipeline نباید از این عبارت نتیجه بگیرد که همه اسناد فوراً effective شده‌اند. نفاذ هر سند یا کل بسته باید یا در همان تصمیم صریحاً تعیین شده باشد یا در تصمیم بعدی انجام شود.

همین قاعده درباره public baseline نیز برقرار است.

---

## ۵. Scope تغییرات مجاز در مرحله ثبت

مرحله ثبت مجاز است artifactهای ثبت‌شده جدید، رکوردهای registry لازم و traceability مربوط را ایجاد یا به‌روزرسانی کند. اما نباید:

- source history قبلی را پاک یا بازنویسی کند؛
- نسخه‌های تاریخی را overwrite کند؛
- متن حقوقی جدیدی خارج از Release Candidate بازبینی‌شده تولید کند؛
- ناسازگاری حقوقی تازه را با «اصلاح هنگام ثبت» پنهان کند؛
- ترجمه یا public baseline را بدون review مستقل ارتقا دهد.

اگر در مرحله ثبت نیاز به تغییر متن حقوقی پیدا شود، عملیات ثبت باید متوقف و آن تغییر به چرخه اصلاحیه/بازبینی جداگانه بازگردد.

---

## ۶. خروجی مطلوب از عملیات ثبت آینده

در پایان یک ثبت صحیح باید بتوان برای هر سند دقیقاً پاسخ داد:

- نسخه ثبت‌شده کدام است؟
- source و commit آن چیست؟
- چه کسی و چه زمانی آن را ثبت کرده است؟
- آیا نافذ است یا صرفاً ثبت‌شده؟
- متن کامل معتبر کجاست؟
- provenance هر ماده چیست؟
- کدام نسخه را supersede می‌کند؟
- وضعیت ترجمه‌ها چیست؟
- آیا public baseline به آن منتقل شده یا نه؟

تا زمانی که این زنجیره پاسخ‌پذیر و machine-verifiable نباشد، ثبت کامل تلقی نمی‌شود.

---

## ۷. وضعیت فعلی

این پیشنهاد در Package F فقط **plan** است:

- `applyNow = false`
- نیازمند تصمیم صریح بنیان‌گذار است؛
- `document-registry.json` و `docs-manifest.json` در این Package دست‌نخورده می‌مانند؛
- public baseline و registered releaseهای تاریخی تغییر نمی‌کنند.
