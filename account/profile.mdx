Your EarthCoop profile supplies identity, professional, and residence information used by several product domains. Some fields affect presentation; others can affect canonical system-group membership and governance placement. A profile edit should therefore be understood according to the domain it changes rather than as a generic preference update.

## Profile sections

The current profile experience can include personal information, professional/expertise information, residence/location data, privacy/preferences, and other account-related fields exposed by the live product.

Exact labels and validation rules can evolve. This guide focuses on the durable relationships between profile data and EarthCoop's current group/location architecture.

## Personal information

Identity and demographic fields can support account identity and the system dimensions that depend on verified member data. Age/gender-related system groups, where applicable, are derived from the relevant canonical profile facts rather than created manually by the member.

Privacy controls determine what information other members can see where the current product exposes those controls. Privacy visibility is distinct from whether EarthCoop internally needs a field to apply a membership or governance rule.

## Professional information

Occupation and expertise data are used to derive relevant professional/specialty system-group dimensions. Changing these facts can cause the canonical membership projection to be recalculated.

You should not have to manually reconstruct system memberships that are derived from your canonical profile. The system is responsible for materializing the memberships that follow from the current profile, topology, and membership rules.

<Info>
  User-created groups are different from automatic system groups. A profile change can affect derived system-group membership without implying that every voluntary/user-created membership should be changed.
</Info>

## Primary residence

Your **Primary Residence** is the residence fact used by the canonical location/governance system. It determines the applicable **Governance Area** and the official location-based membership projection according to the actual topology of the place.

EarthCoop does not assume that every place has the same number of administrative levels. The topology can legitimately include cases such as:

- a city with no region;
- a region with no neighborhood;
- a village with no neighborhood;
- rural branches whose valid governance base differs from an urban path.

Registration/profile flows should stop at the valid **base governance area** for that topology rather than forcing artificial levels to exist.

## Official governance membership

The Primary Residence drives official location-based system memberships. At the member's applicable local/base governance level, the current membership rules determine the direct-participation role; higher official levels can be represented through observer/representation logic according to the canonical governance contract.

Changing Primary Residence causes the current canonical memberships to be re-projected for the new residence. That update must not be described as erasing historical election records, prior audit facts, or past votes. Historical governance/election data has its own lifecycle and audit rules.

## Optional local address and community membership

After the required Primary Residence/base-governance selection, a member may add more precise local address information where supported. Micro-levels can include **Street, Alley, Complex, Block, and Building** depending on the local topology.

These lower address details are **optional** for the member flow. They must not be required merely to complete official registration when the valid governance base has already been selected.

Membership at these optional micro-location levels is a **community** participation choice where the current product exposes it; it is not automatically equivalent to official systemic governance/election eligibility.

<Warning>
  Do not infer official election rights from a Street, Alley, Complex, Block, or Building community membership unless the canonical official governance topology explicitly grants them.
</Warning>

## Proposed and pending locations

If the required location is missing, the current location workflow can allow a member to propose a new place. A **proposed / pending** location is not the same as a finally approved reference record, but pending status should not unnecessarily block registration or the related pending system-group projection where the current contract permits continuation.

A pending proposal can be visible to later members so they can choose/support the same proposed place rather than creating duplicates. The support threshold is part of the proposal-review process; **support is not final administrative approval**.

When the required support/review conditions are met, the proposal proceeds through the applicable confirmation workflow. Until then, related groups or memberships can carry a pending state rather than pretending that the location has already received final approval.

## Editing residence safely

When correcting or changing residence:

1. select the actual valid path for the new Primary Residence;
2. let the topology determine the valid base governance area;
3. use a pending proposal if a required real location is missing and the workflow supports it;
4. save the canonical residence change;
5. review the resulting official groups/governance placement;
6. add optional micro-address/community detail separately if desired.

A mistaken topology declaration or residence selection should be corrected through the supported location/governance workflow rather than by inventing duplicate geographic records.

## Preferences and language

Account preferences such as language, calendar, and notification behavior should be read from the options actually exposed by the current product. Documentation should not treat the existence of a translated document set as proof that every application surface is fully translated into every planned language.
